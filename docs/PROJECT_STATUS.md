## 1. Summary

MarketHubTS has a **working application foundation** (M1), an **initial canonical market-domain foundation** (M2), a **provider adapter framework with resilient connectivity** (M3), and the **live-data pipeline** (M4 Stages A/B/D/E). M1 provides centralized validated runtime configuration, reliable SQLite initialization with versioned Drizzle migrations, an API with health/readiness/lifecycle and deliberate network boundaries, a WebUI application shell showing real backend/runtime status, LAN-capable local operation, and Windows-compatible development/production workflows. M2 adds provider-independent canonical market contracts, stable identity rules, catalog persistence, repository/transaction primitives, and a source-independent transactional catalog synchronization service. M3 adds a portable encrypted credential store, independent Upstox/FYERS auth adapters, and a provider registry. M4 Stage A adds canonical live contracts and bounded in-memory live state; Stage B adds the Upstox V3 SDK streaming adapter; Stage D adds the provider-ready backend vertical slice (service notifications, bounded realtime hub, subscription persistence with durable generation, supervisor, REST/SSE, and a locked production driver boundary); Stage E adds the WebUI live-data experience (streaming selections, canonical-field-only live views, and a deterministic SSE client with recovery and refresh); Stage F adds reconnect/recovery/concurrency/resource hardening (terminal driver-instance retirement with at-most-once stop, typed logical-completion outcomes, callback-gated lifecycle ownership, explicit retry exhaustion, abort-safe retry sleep, and deterministic timer seams); Stage C adds the FYERS Data Socket streaming adapter (official `fyers-api-v3@2.4.1`, adapter-only, canonical component updates with adapter-side depth protection).

M5 adds **historical candle persistence** (five-table storage, derived coverage, interval-aware unconfirmed gaps, first-write-wins conflicts, fail-closed retention) and **option-chain snapshot persistence** (canonical envelope, WebUI-owned capture config, on-demand immutability, deletion safety), plus **offline Upstox/FYERS REST adapters** (mocked fetch only) and a **local API/WebUI** for cached reads and config management (Phase 4A). These capabilities exist in code and are covered by deterministic offline tests.

This is **not** a functioning market-data platform: no live provider connection is attempted in Stage D (the production Upstox driver is locked/disabled and real SDK construction is unreachable), no real socket is opened, **no provider-backed historical or option-chain retrieval is activated** (the API composes M5 services with empty provider collections), no live REST verification has been performed, no live provider data availability is established, no bulk exchange catalog download/seeding, no MCP subscription notifications accepted (M6-D/E source and tests are present but not accepted; M6-A delivers the transport foundation; M6-B1 adds catalog-search and event-feed read seams and adapters; M6-B2 registers nine tools over both transports; M6-B3 resources/prompts are implemented and published on `develop` at `0d58bbb`), no watchlists/alerts/scanners/charts, no operational market-data configuration UI, no backup/restore, and no News/X/Twitter/market-wide integrations are implemented. Live-provider verification remains Stage G and requires separate authorization. **M4 Stage G streaming verification and M5 Stage G REST verification are distinct, separately authorized activities** — success in one does not satisfy the other.

### 3.8 M4 Stage F — reconnect/recovery/concurrency/resource hardening (published on `develop`, independent code review passed)

- **Supervisor (`apps/api/src/stream-supervisor.ts`):** mandatory `AbortSignal` on driver `start`/`updateSubscriptions`; `createDriver` factory with lazy acquisition; typed five-variant `OperationOutcome` (`applied`, `failed`, `timed-out`, `callback-retired`, `shutdown`) with supervisor-owned logical completion so the serialized queue is released independently of driver settlement; `appliedGeneration` advances only on `applied`. Every driver instance is terminal — one idempotent retirement owner calls `stop()` at most once, and every restart uses a fresh factory instance (disconnect, error, failed start/update, timeout, callback retirement, shutdown). Instance-level callback gate closed synchronously before abort; both timeout quiescence branches retire; callback-triggered retirement owns the single retry decision; explicit retry exhaustion after both ERROR and DISCONNECTED sets canonical ERROR with a meaningful `lastError`; jittered backoff with no budget reset on start resolution; shutdown releases all outstanding logical completions with `shutdown`.
- **Composition (`apps/api/src/index.ts`):** `createDriver: () => new LockedUpstoxDriver()` — no real SDK, socket or provider connection; locked driver schedules no retries; factory failure is retried and never classified as locked.
- **WebUI (`apps/web/src/lib/retry-sleep.ts` new, `components/LivePanel.tsx`):** abort-safe retry sleep with listener removal on every terminal path and immediate resolution for an already-aborted signal.
- **Realtime (`packages/realtime/src/hub.ts`, `types.ts`):** narrow `IntervalScheduler` seam with global defaults; refresh timer armed/cleared deterministically; no production telemetry.
