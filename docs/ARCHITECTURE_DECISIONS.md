## 1. Decision log

| ID | Decision | Status | Rationale | Constraints / notes |
|---|---|---|---|---|
| AD-001 | One canonical data and application-services foundation for all consumers (MCP, REST/SSE, WebUI) | **Confirmed** | Prevents inconsistent behavior, duplicate logic, and drift between AI and human interfaces | No independent market-data interpretation or duplicate business logic in MCP/WebUI; shared services only |
| AD-002 | Provider-specific logic isolated in adapters (Upstox, FYERS; extensible) | **Confirmed** | Provider independence, replaceability, and clean normalization boundary | Adapters handle auth, protocol, limits, reconnect, mapping; no provider logic in consumers |
| AD-003 | Both providers operate independently/simultaneously when configured; app works with either or neither (local/non-broker data) | **Confirmed** | Resilience and user choice; no hard dependency on a single broker | One disconnect must not break other; removal must not break remaining functionality |
| AD-004 | Automatic source selection by capability/availability/freshness/reliability/limits; optional manual preferences in WebUI; no fixed provider priority | **Confirmed** | Best available data without hidden bias; user override when needed | Preserve attribution/timestamps; expose restrictions clearly |
| AD-005 | Canonical fields + preserved provider-specific fields + attribution/timestamps/freshness; never fabricate raw provider-supplied market fields (OI, IV, Greeks, prices, depth, volume) | **Confirmed** | Data integrity and trust; extensibility without breaking consumers | Derived technical indicators allowed only as separately labelled derived indicators |
| AD-006 | Live ticks/quotes/depth in memory only; repopulated from streams after restart; no per-tick/per-depth-change persistence | **Confirmed** | Performance, storage efficiency, bounded writes | Must carry source/timestamp/freshness; bounded memory/queues required |
| AD-007 | Historical candles retrieved on demand and/or user-configured sync; cached locally; preserved across disconnect/removal; gap fill from suitable provider when available | **Confirmed** | Useful local history without duplicating entire broker databases | Report unavailable periods/restrictions; retention user-controlled |
| AD-008 | Option-chain snapshots persisted separately per WebUI capture config; streaming selection independent of capture; MCP on-demand does not change capture config | **Confirmed** | Predictable storage and user control; avoids hidden side effects from AI requests | No claims of pre-collection snapshots unless provider supplies them (verify) |
| AD-009 | Common instrument catalog is foundational and shared by all modules/consumers; canonical identity distinct from provider-native IDs; transactional/safe sync | **Confirmed / M2 foundation implemented** | Consistent instrument resolution across product; safe evolution | Dynamic follow of official exchange info; no permanent hardcoding of changing contracts/lot/expiry/strike/freeze. M2 implements normalized identity keys, provider mapping/alias separation, index-eligibility metadata separation, SQLite persistence, and transactional source-independent sync with conflict/failure safety (synthetic/test-validated; no real provider ingestion yet). |
| AD-010 | MCP is primary AI interface using shared services; AI may manage watchlists/alerts/scanners and do on-demand retrieval but cannot modify operational config | **Confirmed** | Powerful AI access with clear safety/control boundary | WebUI owns credentials/connections/streaming/sync/capture/retention/preferences/startup/network |
| AD-011 | Alerts/scanners never auto-subscribe; alerts needing non-streamed instruments saved as waiting with explanation | **Confirmed** | Predictable behavior and user control over streaming/resources | AI must never bypass; scanners report stale/unavailable/not-streamed limitations |
| AD-012 | WebUI is operational control centre; simple configuration, sensible defaults, no hidden fixed policies; provider restrictions exposed clearly | **Confirmed** | Usability and transparency | Never silently change user selections due to API limits |
| AD-013 | Single local owner/application instance (Windows-first, local-first) with **LAN access required** for WebUI and MCP HTTP so other applications/devices/multiple MCP clients can connect to the same running application; local browser-based WebUI acceptable, native desktop wrapper optional; no cloud/public exposure; no app-level user login | **Confirmed** | Target deployment and access model | **Single-user means one local application owner, not one connected client.** Credentials/tokens still handled responsibly (never logged/exposed); secure storage required (verify mechanism). |
| AD-014 | Full backup/restore must include complete DB and any key material/state required to recover encrypted broker credentials; restore tested on clean install | **Confirmed** | Real recoverability, not false confidence | Database-only copy insufficient if keys/state missing |
| AD-015 | Bun + TypeScript monorepo; React/Vite WebUI; Hono API; Zod contracts; SQLite (`bun:sqlite`) + Drizzle; TanStack/Zustand/Tailwind/shadcn; MCP TS SDK; Vela candidate for charts | **Established (baseline/provisional mix)** | Modern, cohesive TS/Bun stack aligned with local-first single-process design | Actual installed versions documented in [DEPENDENCIES.md](DEPENDENCIES.md); Vela and some integrations pending compatibility validation; no dependency changes in this doc task |
| AD-016 | Modular monolith in a single long-running backend process initially (API, broker connections, auth, subscriptions, canonical processing, analytics, scheduling, SSE, DB coordination) | **Established** | Simplicity and shared state/control; avoids premature microservices | Keep responsibilities modular with clear boundaries/interfaces and fault containment per [ENGINEERING_STANDARDS.md](ENGINEERING_STANDARDS.md); no claim of absolute isolation in a shared process; evolve only with demonstrated need |
| AD-017 | SSE primary for frontend realtime delivery; drop overflowing events not subscribers; WebSocket only if justified | **Established** | Simpler client model and resilience under load | Bounded buffers, cleanup, observable drop counters required (planned) |
| AD-018 | MCP transports and event delivery: Streamable HTTP primary network transport; SSE-based event/subscription delivery per current spec using supported `subscriptions/listen` notifications (e.g. `resources/updated`, list changes) with read-after-notify over discoverable resources/feeds; assess legacy HTTP+SSE only for compatibility; retain/document STDIO | **Established, pending verification** | Align with current MCP direction while supporting scaffold/compat needs and reliable alert-event access | Must verify 2026-07-28 spec semantics and `@modelcontextprotocol/server` v2.4.0 behavior before implementation claims. Alert triggers must be durable MarketHub records with event IDs/cursors/sequence, reconnect recovery, independent multi-client consumption, and polling/tool fallback; do not invent arbitrary alert-trigger notification types. |
| AD-019 | No order placement/trading/account-management, no AI recommendations/predictions/signals/sentiment/chat, no general CSV/Excel export | **Confirmed** | Clear product boundary | Watchlist import/export (if retained) is separate |
| AD-020 | News and X/Twitter integrations are required later phases | **Confirmed** | Long-term roadmap completeness | Must remain in architecture/roadmap; not implemented now |
| AD-021 | Portable, self-contained credential storage: encrypted secrets in SQLite with one local key file in the app folder; **no** Windows Credential Manager, `Bun.secrets`, DPAPI, OS keychain or native modules | **Approved by owner (M3)** | Owner requires a fully portable folder and no Windows-linked setup; simplest reliable option with no external service | Built-in Bun crypto only; no plaintext fallback; copying the folder preserves credentials, losing the key requires re-authentication. Accepted tradeoff: a folder copy includes the key and can read secrets — documented openly. AD-014 full-backup requirement is preserved: the folder (DB + key file) is the backup unit; a DB-only copy is not complete. Boundary must stay compatible with future encrypted credential export/import (M9). |
| AD-022 | Upstox uses the Analytics Token (read-only, 1-year, no OAuth, no static IP for market-data categories); FYERS uses V3 individual-app OAuth with a **non-trading (data-only) app** | **Approved by owner (M3)** | Matches the read-only market-data product boundary; avoids daily OAuth for Upstox and FYERS trading-app static-IP mandate | Upstox validation via `GET /v2/market/status/NSE` (not User Profile, which needs static IP); one Analytics Token per account with manual regeneration/revocation explained in UI. FYERS: random state, backend `appIdHash`, single-use code, daily 6:30 AM expiry, no assumed refresh, loopback callback matching registered redirect URI. No trading/account APIs. |
| AD-023 | No hardcoded provider plan limits; design for FYERS Standard and report actual capability/restrictions | **Approved by owner (M3)** | Owner wants to use whatever is available rather than self-imposed caps | Unknown entitlements remain unknown; rate-limit/capability restrictions reported honestly; user settings never silently changed due to limits. FYERS October 16, 2026 limit changes apply. |
| AD-024 | Multi-provider streaming foundation: (A) one shared subscription coordinator owns desired state/persistence/generation and fans out to independent per-provider runtimes; (B) canonical data-component model (quote/depth/derivatives/index/extended) with per-component source selection; (C) provider-neutral capability contracts (no broker SDK mode names in shared contracts) | **PROPOSED — pending independent review and product-owner approval** | Needed for durable simultaneous Upstox+FYERS streaming without redesign; fixes partial-message data loss and cross-provider untrack hazard; preserves Stage F guarantees | Detailed design, alternatives, affected modules, migration and acceptance criteria in [MULTI_PROVIDER_STREAMING_ARCHITECTURE.md](MULTI_PROVIDER_STREAMING_ARCHITECTURE.md). Not an implementation authorization; does not unlock the Stage G production boundary or mark any milestone complete. |

## 3. Superseded / avoided decisions

- **No fixed Upstox-first or FYERS-first priority** (superseded by capability/freshness/reliability/limits-based selection).
- **No permanent hardcoding** of changing exchange contracts/expiries/strikes/lot sizes/quantity freezes.
- **No microservices/external infra by default** (PostgreSQL/Redis/cloud) without demonstrated requirement.
- **No database-only backup** presented as full recovery when credential key material/state is required.
- **No legacy Upstox feed assumptions**; use current V3/official docs (verify).
